01 Recomendação em uma tela

Frontend React + TypeScript, persistência em banco não-relacional (Firestore), código e deploy geridos 100% via GitHub Actions. Nenhum servidor para administrar, funciona offline no tablet da cozinha, e o histórico de perdas nasce auditável — pré-requisito direto para as métricas de perda absoluta/percentual que você pediu.

02 Relação com o Sistema de Gestão (Excel VBA + Access)

Você já tem a construção do Sistema de Gestão autorizada e em andamento (Excel VBA + Access, Google Drive para multi-máquina), com a Fase 1 cobrindo catálogo de produtos, fichas técnicas e estoque. Este app de Produção & Perdas não substitui esse sistema — ele resolve um problema que o Access não resolve bem: entrada de dados pela equipe de produção/balcão, em tempo real, potencialmente em um tablet ou celular na cozinha. VBA/Access são soluções desktop; a rotina diária de "quanto vou produzir hoje" e "quanto perdi no fim do expediente" precisa rodar em qualquer dispositivo, inclusive offline.

Ponto de integração futura O codigoPdv foi mantido como chave primária de produto propositalmente — é o mesmo identificador usado no PDV/Access. Quando o módulo de estoque do Sistema de Gestão estiver pronto, a ponte entre os dois sistemas é uma exportação/sincronização por esse código, sem precisar remodelar nenhum dos dois lados.

03 Stack tecnológica

Persistência de dados — comparação

OpçãoCustoMultiusuário / offlineSem BD relacionalRecomendação
Firestore (Firebase) Gratuito na escala de uma padaria Sim — sincronização em tempo real + cache offline nativo Sim, documento/coleção Recomendado
Google Sheets API Gratuito Fraco — sem suporte offline real, limite de escrita/min Sim, tabular simples Protótipo rápido
JSON versionado no próprio repositório Git Gratuito Não — escrita concorrente gera conflito de merge Sim Só para o catálogo semi-estático

Google Sheets entra como alternativa válida se você preferir zero dependência nova e já pensa em olhar/editar dados direto na planilha — mas fica frágil no fim de expediente, quando mais de uma pessoa pode lançar perdas ao mesmo tempo. JSON-no-Git serve bem para o catálogo de produtos (que muda pouco) mas não para lançamentos diários. Por isso a recomendação separa os dois: catálogo pode nascer de um import versionado; produção e perdas, que mudam todo dia e por múltiplas pessoas, precisam do Firestore.

Papel do GitHub nesta arquitetura

  • Código-fonte completo (React + TS) vive no repositório — é a fonte da verdade, exatamente como pedido.
  • GitHub Actions builda o app a cada push e publica automaticamente no Firebase Hosting (ou Vercel/Netlify, se preferir) — zero passo manual de deploy.
  • O import inicial da planilha (Produtos_881.xlsx) também fica versionado: o script de importação e o relatório de importação vão para o repositório, então qualquer recadastro em lote futuro é rastreável no histórico de commits.

Guardar entradaBruta e quantidadeNormalizada separadamente é o que impede a conversão de "corromper" a métrica: se um peso médio for recalibrado no futuro, dá para reprocessar o histórico sem perder o dado original do operador.

06 Regra de conversão peso ↔ unidade

Exemplo real, validado no código entregue: Pão Francês é produzido e vendido em unidades, com peso médio cadastrado de 50 g. No fim do expediente, o operador pesa a sobra na balança: 1 kg.

entrada:  1 kg
cálculo:  (1 kg × 1000) / 50 g  =  20 unidades
guardado: entradaBruta = { valor: 1, unidade: "kg" }
          quantidadeNormalizada = 20 (un)
          fatorConversaoAplicado = true

Se o produto não tiver peso médio cadastrado, o sistema recusa o lançamento em kg com uma mensagem explícita ("cadastre o peso médio antes de lançar em kg") — nunca assume um valor, nunca falha silenciosamente. As mesmas 13 verificações abaixo cobrem esse e outros casos de borda.

Cronograma de Produção Seleciona dia da semana e sessão (fixa/especial), escolhe produtos do catálogo, digita quantidade. Sem fotos — só código, nome e número, como pedido.
Resumo pré-salvamento Lista consolidada por sessão antes de confirmar — última chance de conferir/ajustar. Só vira "confirmado" a partir daqui.
Cadastro de Produtos Form rápido para item novo + botão "Importar Planilha" (mesma lógica do script entregue, rodando no navegador).
Registro de Perdas Um produto por vez, campo numérico + toggle kg/un quando aplicável, preview de conversão instantâneo, motivo do descarte.

As três funções são puras (sem I/O) e recebem os dados já filtrados por período — a decisão de "últimos 30 dias" ou "mês fechado" fica na camada de consulta, não na lógica de cálculo. Isso facilita testar e trocar a fonte de dados (Firestore hoje, outra coisa amanhã) sem reescrever a matemática.

09 Roadmap sugerido

  1. Fase 0 — Fundação (1 semana): criar repositório GitHub, scaffold Vite+React+TS, Firebase configurado, pipeline de deploy via Actions.
  2. Fase 1 — Catálogo: importar os 881 produtos, revisar categorias "SEM_CATEGORIA", tela de Cadastro de Produtos funcionando.
  3. Fase 2 — Cronograma + Resumo: fluxo completo de planejamento diário, sessões fixas e especiais.
  4. Fase 3 — Perdas: tela de registro com conversão, cadastro de peso médio por produto habilitado.
  5. Fase 4 — Análises: dashboards de taxa de perda, volume por dia da semana, picos por categoria.
  6. Fase 5 — Integração: ponte com o Sistema de Gestão (Access) via codigoPdv, quando o módulo de estoque estiver pronto.
